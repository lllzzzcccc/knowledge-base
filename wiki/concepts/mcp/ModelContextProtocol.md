# 模型上下文协议 (MCP)

MCP 是由 [[Anthropic]] 推出的开放协议,用于连接大型语言模型与外部工具、数据源和应用系统。它为 AI 模型提供标准化的方式来获取上下文信息并执行实际操作,开发者可将文件系统、数据库、API、企业系统封装为"可调用资源"。常被类比为"AI 应用程序的 USB-C 接口"——为模型与外设(工具/数据)提供统一连接标准。

## 架构:客户端-服务器

MCP 采用分布式客户端-服务器架构,通信涉及三个角色([[mcp-explained]]):

- **MCP Host**:启动 LLM 连接的应用程序(如 Cursor、Claude Desktop、Cline)。
- **MCP Client**:运行在 AI 应用/IDE/Agent 中的客户端组件,是 AI 的"调度与通信层"——建立连接、发现能力([[MCPTool]]/[[MCPResource]]/[[MCPPrompt]])、把模型的工具调用请求转成协议消息、将结果整合回模型上下文。
- **MCP Server**:能力网关,向 Client 暴露资源和工具,收到请求后执行具体操作(读文件、查数据库、调 API、运行命令),内部含工具注册、资源管理、执行引擎与安全控制模块。

## 三大核心原语

- [[MCPTool]] — 可执行能力模块,类似函数调用,会改变系统状态。
- [[MCPResource]] — 只读数据资源,只提供上下文,不执行操作。
- [[MCPPrompt]] — 标准化任务模板,规范模型行为与任务流程。

Tools 与 Resources 共同构成 AI 可访问的数据与功能集合。

## 工作流程(七步)

1. 客户端与服务器建立连接
2. 双方确认沟通规则(协商)
3. 客户端询问可用工具/资源/提示,服务器返回能力清单
4. LLM 接受用户请求后思考,决定用哪个工具并传参
5. 客户端把请求转换为标准格式(JSON-RPC)发给服务器
6. 服务器调用外部系统执行操作
7. 结果经服务器→客户端→LLM 逐级回传,上下文更新

## 通信机制

通信协议统一为 **JSON-RPC**,但传输方式有三种:

| 传输方式 | 机制 | 特点 | 现状 |
|---|---|---|---|
| STDIO | 父子进程 stdin/stdout 传输 JSON-RPC | 无网络、低延迟、强隔离;要求纯净 JSON 输出不能混入日志;本质是"本地进程级 RPC 通道" | 默认、最核心 |
| SSE | HTTP 单向事件流,服务端持续推送 | 实现简单、天然流式、易穿透防火墙;但单向,需配 REST API 补全请求-响应 | 官方已弃用 |
| Streamable HTTP | HTTP POST + 可选流式响应 | 兼顾请求-响应与流式输出;易集成认证、网关、负载均衡等云原生设施 | 官方推荐 |

适用场景:STDIO 用于本地工具/插件/开发调试/隐私数据处理;Streamable HTTP 适合远程服务化部署与企业级扩展。

## 与操作系统 IPC 的对应

- STDIO 父子进程通信复用了操作系统[[Pipe]](匿名管道)机制——进程间通信用途在 AI 协议层的实例。
- SSE/Streamable HTTP 基于网络通信,属于[[Socket]]所覆盖的跨网络进程通信范畴。

## 价值定位

MCP 的价值不在于替代现有架构,而在于解耦模型与工具之间的交互复杂度,使开发者专注业务逻辑而非接口适配与上下文拼接——为构建可扩展、可组合的 AI 应用提供基础设施级支撑。
