# IO 多路复用 (I/O Multiplexing)

多路复用一句话点破:**"阻塞"本身没错,错的是"每个连接都占一个线程去阻塞"。多路复用让一个线程一次性阻塞在很多个连接上,哪个有数据了内核就叫醒它,它再单独处理那个**([[claude-concurrency-io-session]])。

## 1. 线程 read() 阻塞时内核发生了什么

线程调 `read(fd)` 进入内核([[UserModeVsKernelMode]]):socket 接收缓冲区**有数据**→ 拷贝返回;**没数据** → 内核把该线程挂到该 fd 的**等待队列(wait queue)**,切换到别的线程。数据到达后内核去等待队列唤醒线程。

**每个 socket 都有一个等待队列,挂着正在等它的线程。**

## 2. BIO 的浪费

一万个连接 → 一万个线程,每个挂在一个 fd 上等。线程 99% 时间在睡觉,却每个都占内存(栈)、参与调度——这就是 C10K 问题:**线程不够用、调度不过来**。

## 3. 非阻塞的坑:忙轮询

`O_NONBLOCK` 下 `read()` 没数据立即返回(EAGAIN),线程不睡——但得不停"问",CPU 空转 100%,比阻塞还浪费。**非阻塞单独用时的死穴:把"睡觉等待"换成"疯狂空转"。**

## 4. 关键洞察

让内核提供一种能力:**一个线程,一次调用,同时等待 N 个 fd,任何一个就绪就返回并告诉你是哪些。** 模型对比:

- BIO:**10000 个线程**,每个挂在一个 fd 上等
- 多路复用:**1 个线程**,挂在 10000 个 fd 上等

"多路复用"四字拆开:**多路**(很多连接)**复用**(共用一个线程、一次等待)。

## 5. 内核实现:epoll_wait 与等待队列

`epoll_wait()` 执行时:内核把当前这一个线程同时登记到所有监听 fd 的等待队列 → 线程睡眠 → 某 fd 有数据,内核唤醒该线程并标记就绪 → `epoll_wait` 返回就绪列表 → 线程只对就绪 fd `read()`(数据已在,立即返回不阻塞)。**一次 sleep 覆盖所有 fd,一次唤醒精确告知谁就绪。**

## 6. select / poll / epoll 对比

| | select | poll | epoll |
|---|---|---|---|
| 找"谁就绪" | 内核遍历全部 fd,O(n) | 同左 O(n) | 维护**就绪链表**,直接取 O(1) |
| fd 集合传递 | `fd_set` 每次整份拷进内核 | 数组,每次拷 | `epoll_ctl` **只注册一次** |
| fd 上限 | 默认 1024 | 无上限(性能仍 O(n)) | 无上限 |

epoll 快的两个关键:**注册一次永久有效**(红黑树管理监听集合);**就绪链表 + 回调**(fd 就绪即经回调挂入链表,`epoll_wait` 直接取回,不遍历)。

## 7. 餐厅类比

BIO = 每桌配一个服务员站桌边等点菜;非阻塞轮询 = 一个服务员绕 100 桌狂奔挨个问;多路复用 = 每桌一个**按铃**,一个服务员坐前台,哪桌按铃才过去服务。select/poll 是没有按铃、定期全店扫一遍;epoll 是装了按铃直接知道哪桌。

## 关联概念

- [[IOModels]] — 多路复用是 NIO 的核心机制
- [[EventLoop]] — 事件循环把 epoll 再包一层:就绪事件入队,单线程串行执行回调
- [[Goroutine]] — Go 的 netpoller 直接复用本页这套 epoll 机制,让协程"阻塞却不占线程"
- [[Socket]] — epoll 监听的 fd 主要就是 socket
- [[Thread]] — 用 1 个线程替代 N 个阻塞线程的关键
