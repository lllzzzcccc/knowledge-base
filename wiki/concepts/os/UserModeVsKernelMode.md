# 用户态与内核态 (User Mode & Kernel Mode)

CPU 的特权级机制：用户态代码被限制在自己地址空间内运行，内核态代码可访问全部硬件与系统资源。程序需要内核代劳做的事，通过**系统调用**陷入（trap）内核态完成，结束后返回用户态。这条边界是 [[Process]] 地址空间隔离（[[process-vs-thread]]）与"[[IPC]] 必须经内核"（[[six-ipc-mechanisms]]）的硬件基础。

## 判断一行代码是否陷入内核态

**核心判据：这行代码做的事，若由用户程序自己动手，会不会破坏保护机制或干扰其他进程？——会，就要陷入；不会，就留在用户态。**

| 资源/动作 | 例子 | 系统调用 |
|---|---|---|
| 文件/网络/终端 I/O | 读写磁盘文件、socket 收发 | `read`/`write`/`open` |
| 内存疆域扩张 | 申请大块新堆内存 | `brk`/`mmap` |
| 进程控制 | 创建进程、等待、发信号 | `fork`/`waitpid`/`kill`（[[Signal]]） |
| 进程间通信 | 管道、消息队列、共享内存 | `pipe`/`mq_*`/`shmget`（[[IPC]]） |

对照面：只在自己地址空间内操作数据（算术、指针、容器增删、`strlen`）→ 纯用户态，不陷入。

### 两个反直觉陷阱

**看起来会、实际暂时没有（缓冲层）**：
- `printf`/`std::cout` 通常只把字符拷进**用户态缓冲区**；缓冲区满、遇 `endl`（tty 行缓冲）或退出 flush 时才真正 `write` 陷入——是否陷入取决于运行时状态。
- `malloc`/`free` 复用堆内空闲块时纯用户态；堆不够用需扩张时才 `brk`/`mmap` 陷入。

**看起来不会、实际会（隐藏调用）**：
- `std::thread` 底层是 `clone`；`system()` 底层是 `fork`+`execve`；大 `vector` 扩容可能触发 `mmap`。

### 查证方法

1. man 手册第 2 节 = 系统调用；第 3 节 C 库函数看其内部封装。
2. `strace ./程序`（Linux）：逐行打印每次系统调用及参数，最可靠的证据。
3. Windows 无 strace，用 Process Monitor 或 VS 诊断工具观察。

### 例外：vDSO

`time()`、`getpid()` 等只读系统信息，内核通过 vDSO 把数据页映射进每个进程的用户地址空间，读时间变成普通内存读取，**不陷入**。说明判据本质是"是否需要内核执行特权操作"，而非"是否与系统有关"。

## 与上下文切换的关系

二者是两种开销完全不同的内核动作（[[ContextSwitch]]）：

- **陷入/返回（mode switch，便宜）**：每个系统调用都是；只切 CPU 特权级、保存少量寄存器，几十 ns~µs。
- **进程上下文切换（贵 10~100 倍）**：进程阻塞时调度器完整保存/恢复全套寄存器并切换页表（地址空间信息）。

## 关联概念

- [[AddressSpaceLayout]] — 用户/内核两半空间的布局、权限位与数据通路
- [[Process]]：地址空间隔离是用户态限制的体现；[[Thread]]：同进程线程共享地址空间，无需 IPC
- [[ContextSwitch]]：陷入是轻量切换，进程切换是重量切换
- [[IPC]] / [[MessageQueue]] / [[SharedMemory]]：通信机制的"是否经内核"决定其陷入次数与性能档位
