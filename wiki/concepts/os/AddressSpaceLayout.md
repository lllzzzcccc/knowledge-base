# 进程地址空间布局 (Address Space Layout)

**每个进程的虚拟地址空间分成两半：低地址的"用户空间"（进程私有）+ 高地址的"内核空间"（所有进程共享同一份内核）。** 进程平时只能访问用户空间；内核空间是"只能看不能摸"的禁区，唯一合法的进入方式是系统调用。

## 空间图

```
4G ┌─────────────────┐
   │    内核空间       │ ← 所有进程映射到【同一块物理内存】
   │  (约 3G~4G)      │   内核代码、内核数据结构、
   │                 │   每个 socket 的收发缓冲区……
3G ├─────────────────┤ ← 经典 3:1 分界（Linux 32位；
   │    栈 ↓          │   64 位理论对半分，窗口巨大）
   │  .........      │
   │    堆 ↑          │ ← 用户空间，进程私有
   │    数据区        │   （[[Process]] 的代码区/数据区/堆栈区
   │    代码区        │     全部属于这一半）
0  └─────────────────┘
```

## 三个关键认知

**1. 这是虚拟地址空间的划分，不是物理内存的划分。** 每个进程有一套完整的虚拟地址编号，MMU + 页表负责翻译成物理地址。分两半的本质是**页表项的权限位**不同：用户空间页标记"用户可访问"，内核空间页标记"仅内核态可访问"。

**2. CPU 特权级是执行时的闸门。** 用户态下硬件拦截对内核页的访问——进程直接用指针读内核地址立刻触发页保护异常被杀掉（[[UserModeVsKernelMode]]）。所以分两半不是软件约定，是硬件强制。

**3. 内核空间装着"同一份内核"。** 所有进程页表的内核空间部分映射到相同物理页——你进程里的 3G 处和别的进程里的 3G 处是同一扇窗。这就是"内核空间共享"的含义，也是 [[IPC]] 必须经内核的物理基础：进程 A 把数据写进内核（如 [[Pipe]] 缓冲区），B 从同一块内核内存读到。共享内存（[[SharedMemory]]）是唯一例外——在两进程用户空间各映射同一物理页，读写完全不过内核。

## 数据如何跨空间流动

以 `read(fd, buf, size)` 为例：

```
网卡数据 → DMA 拷入【内核空间】的 socket 接收缓冲区
              │
线程调 read()，陷入内核（特权级切换 + 换内核栈，[[ContextSwitch]]）
              │
内核把数据从内核缓冲区拷到 buf（用户空间）
              │
返回用户态，线程拿到数据
```

一次网络读取至少一次**跨空间拷贝**——"零拷贝"（sendfile、mmap）优化的就是这个。BIO 里线程"等数据"，等的就是内核缓冲区（[[IOMultiplexing]] 的等待队列也在内核空间）。

## 与协程的关系

协程没有消除这个边界，但把"过边界的频率和代价"压到最低：调度决策搬回用户态、等待改为用户态挂起，只有极少线程在内核边上轮询。详见 [[Goroutine]]。

## 关联概念

- [[UserModeVsKernelMode]] — 两半空间的访问规则是该页的内存版表述
- [[Process]] — 用户空间的三区结构；[[Thread]] — 同进程线程共享整个布局
- [[ContextSwitch]] — 陷入内核要换栈，两套栈分居两个空间

- [[JvmRuntimeMemory]] — JVM 对用户空间的逻辑分区；[[JavaMemoryModel]] — 其上的并发访问规范
- [[JVM]] — 租户本身：进程内执行字节码的语言运行时
